# Payment Payload Gap Analysis

> **Scope**: Fund Transfer Service, Utility Payment Service, and Core Banking Service payment processing  
> **Standard**: ISO 20022 — `pain.001` (Customer Credit Transfer Initiation), `pain.002` (Payment Status Report), `pacs.008` (FI-to-FI Customer Credit Transfer)  
> **Date**: 2026-05-13

---

## 1. Current Payment Payload Structure

### 1.1 Fund Transfer — Request / Response

#### Orchestration Layer (`internet-banking-fund-transfer-service`)

**Request — `FundTransferRequest`**

| Field         | Type         | Description                         |
|---------------|-------------|-------------------------------------|
| `fromAccount` | `String`    | Source account number                |
| `toAccount`   | `String`    | Destination account number           |
| `amount`      | `BigDecimal`| Transfer amount (no currency field)  |
| `authID`      | `String`    | Authenticated user identifier        |

**Response — `FundTransferResponse`**

| Field           | Type     | Description                            |
|-----------------|---------|----------------------------------------|
| `message`       | `String`| Human-readable result text             |
| `transactionId` | `String`| UUID generated by core-banking-service |

#### Core Layer (`core-banking-service`)

**Request — `FundTransferRequest`** (separate class, same package path)

| Field         | Type         | Description                              |
|---------------|-------------|------------------------------------------|
| `fromAccount` | `String`    | Source account number                     |

| `amount`      | `BigDecimal`| Transfer amount                           |

> Note: The orchestration-layer request carries `authID`; the core-layer request does not. The orchestration service strips `authID` implicitly via `BeanUtils.copyProperties` before Feign forwarding.

## 2. ISO 20022 Comparison

### 2.1 Mapping to `pain.001` — Customer Credit Transfer Initiation

The `pain.001` message is the standard for a customer instructing their bank to execute a credit transfer. The table below maps mandatory / commonly-used ISO 20022 elements to current payload fields.

| ISO 20022 Element (`pain.001`)             | Current Field                          | Status                  | Notes                                                                 |
|--------------------------------------------|----------------------------------------|-------------------------|-----------------------------------------------------------------------|
| `MsgId` (Message Identification)           | —                                      | **MISSING**             | No message-level identifier; only transaction-level UUID exists        |
| `CreDtTm` (Creation Date Time)             | `AuditAware.createdDate`               | **PARTIAL — renamed**   | Exists on entity but not in request/response payloads                  |
| `NbOfTxs` (Number of Transactions)         | —                                      | **MISSING**             | System processes single transactions only; no batch support            |
| `CtrlSum` (Control Sum)                    | —                                      | **MISSING**             | No batch control; no checksum for integrity verification               |
| `InitgPty` (Initiating Party)              | `authID` (fund transfer only)          | **PARTIAL — minimal**   | Only a Keycloak subject ID; no structured party block (name/address)   |
| `PmtInfId` (Payment Information ID)        | —                                      | **MISSING**             | No payment-instruction-level grouping identifier                       |
| `PmtMtd` (Payment Method)                  | —                                      | **MISSING**             | Always implicit credit transfer; not declared                          |
| `ReqdExctnDt` (Requested Execution Date)   | —                                      | **MISSING**             | No scheduled / future-dated payments supported                         |
| `Dbtr` (Debtor — structured party)         | `fromAccount` / `account`              | **PARTIAL — flat**      | Account number only; no debtor name, address, or identification block  |
| `DbtrAcct` (Debtor Account — IBAN/BBAN)    | `fromAccount` / `account` (plain str)  | **PARTIAL — non-standard** | Plain string; no IBAN/BBAN structure, no currency, no account type  |
| `DbtrAgt` (Debtor Agent — BIC)             | —                                      | **MISSING**             | Single-bank system; no BIC/SWIFT routing                               |
| `CdtrAgt` (Creditor Agent — BIC)           | —                                      | **MISSING**             | Same as above                                                          |
| `Cdtr` (Creditor — structured party)       | `toAccount` / `providerName`           | **PARTIAL — flat**      | Account number or provider name only; no structured creditor block     |
| `CdtrAcct` (Creditor Account — IBAN/BBAN)  | `toAccount`                            | **PARTIAL — non-standard** | Plain string; no standard account identification                    |
| `Amt/InstdAmt` (Instructed Amount + Ccy)   | `amount` (BigDecimal)                  | **PARTIAL — no currency** | Amount present but currency code is completely absent                |

| `ChrgBr` (Charge Bearer)                   | —                                      | **MISSING**             | No fee/charge model declared                                           |
| `EndToEndId` (End-to-End Identification)   | `transactionId` (response-only UUID)   | **PARTIAL — server-side** | Generated server-side; client cannot supply their own E2E ID        |

## 3. Payment Validation Rules Assessment

### 3.1 Amount Validation

| Rule                           | Implemented? | Details                                                                 |
|--------------------------------|-------------|-------------------------------------------------------------------------|
| Amount > 0                     | **NO**      | No positive-amount check. Zero or negative amounts are accepted.         |
| Maximum transfer limit         | **NO**      | No per-transaction, daily, or account-level limits enforced.             |
| Minimum transfer amount        | **NO**      | No minimum threshold.                                                    |
| Sufficient balance             | **YES**     | `TransactionService.validateBalance()` checks `actualBalance >= amount`. |
| Amount precision / scale       | **NO**      | `BigDecimal` used but no scale enforcement (e.g., 2 decimal places).     |

### 3.2 Currency Handling

| Rule                                | Implemented? | Details                                                          |
|-------------------------------------|-------------|------------------------------------------------------------------|
| Currency code on request            | **NO**      | No currency field anywhere in the payload or entity model.        |
| Multi-currency support              | **NO**      | Implicit single-currency assumption; no exchange rate handling.    |
| Currency mismatch validation        | **NO**      | Not applicable since currency is absent.                          |
| Currency stored on account          | **NO**      | `BankAccountEntity` has no currency column.                       |

### 3.3 Duplicate Detection / Idempotency

| Rule                                | Implemented? | Details                                                                        |
|-------------------------------------|-------------|--------------------------------------------------------------------------------|
| Client-supplied idempotency key     | **NO**      | No `Idempotency-Key` header or client-generated request ID accepted.            |
| Duplicate transfer detection        | **NO**      | Identical fund transfer requests (same from/to/amount) are processed multiple times. |
| Duplicate utility payment detection | **NO**      | Same `referenceNumber` + `providerId` can be paid repeatedly.                    |
| `transactionId` uniqueness          | **PARTIAL** | UUID is generated server-side; unique per invocation but provides no client dedup.|

### 3.4 Account Validation

| Rule                                | Implemented? | Details                                                               |
|-------------------------------------|-------------|-----------------------------------------------------------------------|
| Account existence                   | **YES**     | `AccountService.readBankAccount()` throws `EntityNotFoundException`.   |
| Account status check (ACTIVE)       | **NO**      | `DORMANT` or `BLOCKED` accounts can still send/receive transfers.      |
| Self-transfer prevention            | **NO**      | Same fromAccount and toAccount is permitted.                           |
| Provider existence (utility)        | **YES**     | `readUtilityAccount(providerId)` throws if not found.                  |

### 3.5 Error Handling & Transaction Safety

| Rule                                    | Implemented? | Details                                                                               |
|-----------------------------------------|-------------|---------------------------------------------------------------------------------------|
| Atomic transaction (debit + credit)     | **PARTIAL** | `@Transactional` on `TransactionService` covers core DB ops, but Feign call is outside the transaction boundary. |
| Compensation / rollback on failure      | **NO**      | If core-banking call fails, orchestration entity stays `PENDING`/`PROCESSING` forever.  |
| Proper HTTP status codes                | **NO**      | `GlobalExceptionHandler` returns `400 Bad Request` for all errors including server errors, not-found, and insufficient funds. |
| Structured error response               | **PARTIAL** | `ErrorResponse(code, message)` for `SimpleBankingGlobalException`; raw string for all other exceptions. |

### 3.6 Known Bugs Affecting Payment Integrity

| Bug                                | Severity     | Details                                                                                                  |
|------------------------------------|-------------|----------------------------------------------------------------------------------------------------------|
| Double-deduction in fund transfer  | **CRITICAL** | `internalFundTransfer()` sets `availableBalance = actualBalance - amount` AFTER `actualBalance` was already debited, causing double subtraction. |
| Double-deduction in utility payment| **CRITICAL** | `utilPayment()` same pattern: `availableBalance` computed from already-debited `actualBalance`.            |
| Double-addition on credit side     | **HIGH**     | `toBankAccountEntity.setAvailableBalance(actualBalance + amount)` AFTER `actualBalance` was already credited, inflating available balance. |

## 5. Summary

The current payment domain provides **basic fund transfer and utility payment** functionality with minimal validation. Out of ~25 key ISO 20022 data elements assessed:

- **0 fields** are fully ISO 20022 compliant
- **10 fields** are partially present (exist but are named differently, structurally flat, or missing required attributes like currency)
- **15+ fields** are completely absent

**Top 3 priorities for ISO 20022 alignment:**

1. **Add currency support** — Add a `currency` field (ISO 4217) to all payment requests, responses, and account entities. This is the single most impactful change for regulatory compliance.
2. **Fix the double-deduction/addition bug** — The arithmetic error in `TransactionService` causes incorrect balances on every transaction and is a direct financial integrity issue.
3. **Implement idempotency** — Add client-supplied `EndToEndId` / idempotency keys and server-side duplicate detection to prevent double-processing on retries.
