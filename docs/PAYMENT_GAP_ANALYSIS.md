# Payment Payload Gap Analysis

> **Scope**: Fund Transfer Service (`internet-banking-fund-transfer-service`) and Utility Payment Service (`internet-banking-utility-payment-service`), including their delegation to Core Banking Service (`core-banking-service`).
>
> **Benchmark**: ISO 20022 payment message standards — `pain.001` (Customer Credit Transfer Initiation), `pain.002` (Payment Status Report), `pacs.008` (FI-to-FI Customer Credit Transfer).

---

## 1. Current Payment Payload Structure

### 1.1 Fund Transfer — Request / Response

#### Initiation Request (Fund Transfer Service → exposed via `POST /api/v1/transfer`)

| Field | Type | Description |
|---|---|---|
| `fromAccount` | `String` | Source account number |
| `toAccount` | `String` | Destination account number |
| `amount` | `BigDecimal` | Transfer amount |
| `authID` | `String` | Authenticated user identifier (passed from gateway header) |

#### Core Banking Request (Fund Transfer Service → Core Banking via Feign `POST /api/v1/transaction/fund-transfer`)

| Field | Type | Description |
|---|---|---|
| `fromAccount` | `String` | Source account number |
| `toAccount` | `String` | Destination account number |
| `amount` | `BigDecimal` | Transfer amount |

> **Note:** The `authID` field is stripped when forwarding to core banking — core banking receives a 3-field subset.

#### Response (both layers)

| Field | Type | Description |
|---|---|---|
| `message` | `String` | Human-readable result text |
| `transactionId` | `String` | UUID generated by core banking |

#### Persisted Entity (`fund_transfer` table)

| Column | Type | Description |
|---|---|---|
| `id` | `BIGINT` (auto) | Surrogate PK |
| `transaction_reference` | `VARCHAR` | Maps to `transactionId` from response |
| `from_account` | `VARCHAR` | Source account |
| `to_account` | `VARCHAR` | Destination account |
| `amount` | `DECIMAL(19,2)` | Transfer amount |
| `status` | `ENUM(PENDING,SUCCESS)` | Transfer lifecycle state |
| `created_date` / `modified_date` | `INSTANT` | Audit timestamps |
| `created_by` / `modified_by` | `VARCHAR` | Audit user |
| `version` | `BIGINT` | Optimistic locking |

| Field | Type | Description |

## 2. ISO 20022 Comparison

### 2.1 pain.001 — Customer Credit Transfer Initiation

ISO 20022 `pain.001` defines the message a customer sends to their bank to initiate a credit transfer. Below maps the standard's key fields against the current fund transfer request.

| ISO 20022 Field (pain.001) | XPath | Current Equivalent | Status |
|---|---|---|---|
| **Message Identification** | `GrpHdr/MsgId` | *(none)* | **MISSING** |
| **Creation Date Time** | `GrpHdr/CreDtTm` | `createdDate` (audit) | Present (named differently — audit field, not in request) |
| **Number of Transactions** | `GrpHdr/NbOfTxs` | *(none — single-tx only)* | **MISSING** |
| **Control Sum** | `GrpHdr/CtrlSum` | *(none)* | **MISSING** |
| **Initiating Party** | `GrpHdr/InitgPty/Nm` | `authID` (Keycloak UUID) | Present (named differently — no structured party name) |
| **Payment Information ID** | `PmtInf/PmtInfId` | *(none)* | **MISSING** |
| **Payment Method** | `PmtInf/PmtMtd` (TRF, CHK, etc.) | *(none — always transfer)* | **MISSING** |
| **Requested Execution Date** | `PmtInf/ReqdExctnDt` | *(none — immediate only)* | **MISSING** |
| **Debtor Name** | `PmtInf/Dbtr/Nm` | *(none)* | **MISSING** |
| **Debtor Account IBAN** | `PmtInf/DbtrAcct/Id/IBAN` | `fromAccount` (proprietary number) | Present (named differently — not IBAN format) |
| **Debtor Agent BIC** | `PmtInf/DbtrAgt/FinInstnId/BICFI` | *(none — single-bank system)* | **MISSING** |
| **Creditor Name** | `CdtTrfTxInf/Cdtr/Nm` | *(none)* | **MISSING** |
| **Creditor Account IBAN** | `CdtTrfTxInf/CdtrAcct/Id/IBAN` | `toAccount` (proprietary number) | Present (named differently — not IBAN format) |
| **Creditor Agent BIC** | `CdtTrfTxInf/CdtrAgt/FinInstnId/BICFI` | *(none)* | **MISSING** |
| **Amount + Currency** | `CdtTrfTxInf/Amt/InstdAmt Ccy` | `amount` (BigDecimal, **no currency**) | **PARTIAL** — amount present, currency missing |
| **End-to-End Identification** | `CdtTrfTxInf/PmtId/EndToEndId` | *(none)* | **MISSING** |
| **Instruction Identification** | `CdtTrfTxInf/PmtId/InstrId` | *(none)* | **MISSING** |
| **Remittance Information** | `CdtTrfTxInf/RmtInf/Ustrd` | *(none — no memo/narration)* | **MISSING** |
| **Purpose Code** | `CdtTrfTxInf/Purp/Cd` | *(none)* | **MISSING** |
| **Charge Bearer** | `CdtTrfTxInf/ChrgBr` (DEBT, CRED, SHAR) | *(none)* | **MISSING** |

#### Extra Fields (not in pain.001)

| Current Field | Notes |
|---|---|
| `authID` | Gateway-injected header; ISO uses `InitgPty` with structured identity |

## 3. Payment Validation Rules Assessment

### 3.1 Amount Limits

| Check | Implemented? | Details |
|---|---|---|
| Minimum transfer amount (> 0) | **NO** | No `@Min`, `@Positive`, or manual check. Negative/zero amounts processed. |
| Maximum transfer amount | **NO** | No upper limit configured. |
| Daily/monthly transfer limits | **NO** | No cumulative limit tracking. |
| Amount precision/scale | **PARTIAL** | `BigDecimal` used, but no rounding mode. DB column is `DECIMAL(19,2)`. |

### 3.2 Currency Handling

| Check | Implemented? | Details |
|---|---|---|
| Currency field on request | **NO** | No currency in any request DTO. |
| Multi-currency support | **NO** | Single implicit currency assumed. |
| Currency mismatch validation | **NO** | Account has no currency field — cannot validate. |
| FX rate application | **NO** | Not applicable without currency. |

### 3.3 Duplicate Detection

| Check | Implemented? | Details |
|---|---|---|
| Idempotency key on request | **NO** | No idempotency key / `X-Idempotency-Key` header. |
| Duplicate transfer detection | **NO** | Same transfer can be submitted multiple times. Each creates a new `fund_transfer` row. |
| Duplicate utility payment detection | **NO** | Same payment can be submitted multiple times. Each creates a new `utility_payment` row. |
| Reference number uniqueness | **NO** | `referenceNumber` on utility payments is not validated for uniqueness. |

### 3.4 Account Validation

| Check | Implemented? | Details |
|---|---|---|
| Account existence | **YES** | `AccountService.readBankAccount()` throws `EntityNotFoundException` if account not found. |
| Account status check (ACTIVE) | **NO** | Account has a `status` field (`PENDING`, `ACTIVE`, `DORMANT`, `BLOCKED`) but **no validation** — transfers proceed from blocked/dormant accounts. |
| Self-transfer prevention | **NO** | `fromAccount == toAccount` is not checked. |
| Account ownership verification | **NO** | No check that `authID` owns the `fromAccount`. Any authenticated user can debit any account. |

### 3.5 Balance Validation

| Check | Implemented? | Details |
|---|---|---|
| Sufficient balance | **YES** | `validateBalance()` checks `actualBalance >= amount` and `actualBalance >= 0`. |
| Double-deduction bug | **CRITICAL BUG** | `internalFundTransfer()` sets `availableBalance = actualBalance - amount` **after** `actualBalance` was already debited. This causes `availableBalance` to be debited twice. Same bug in `utilPayment()`. |
| Concurrent transaction safety | **PARTIAL** | `@Transactional` on `TransactionService` provides DB-level isolation, but no explicit pessimistic/optimistic locking on the account row. Race conditions possible. |

### 3.6 Error Handling

| Check | Implemented? | Details |
|---|---|---|
| Structured error responses | **PARTIAL** | `GlobalExceptionHandler` returns `ErrorResponse(code, message)` for known exceptions, but generic `Exception` returns a raw string. |
| HTTP status codes | **NO** | All errors return HTTP 400 (`badRequest()`), including 404-type (account not found), 422-type (insufficient funds), and 500-type (unexpected errors). |
| Feign error propagation | **NO** | No `FeignErrorDecoder` in fund-transfer or utility-payment services. Raw Feign exceptions propagate. |
| Compensation/rollback on failure | **NO** | If the Feign call to core banking fails, `fund_transfer` stays `PENDING` and `utility_payment` stays `PROCESSING` forever. No retry, no saga, no compensation. |

## 4. Gap Severity & Business Risk Rating

| # | Gap | Severity | Business Risk | Category |
|---|---|---|---|---|
| G-01 | **No currency field** — amount has no currency qualifier | **Critical** | Multi-currency transactions impossible; regulatory non-compliance for cross-border | ISO Compliance |
| G-02 | **Double-deduction bug** — `availableBalance` computed from already-debited `actualBalance` | **Critical** | Customer money loss on every transaction | Financial Integrity |
| G-03 | **No idempotency** — duplicate submissions create duplicate transactions | **Critical** | Double-charging customers on network retries or UI double-clicks | Financial Integrity |
| G-04 | **No account ownership check** — any user can debit any account | **Critical** | Unauthorized fund transfers; regulatory violation | Security |
| G-05 | **No account status validation** — blocked/dormant accounts can transact | **High** | Regulatory hold/freeze orders ineffective | Compliance |
| G-06 | **No input validation** — null/negative amounts not rejected | **High** | NPE crashes, negative transfers (reverse fund flow) | Reliability |
| G-07 | **No compensation on Feign failure** — orphaned PENDING/PROCESSING records | **High** | Funds debited in core but status never updated; customer confusion | Reliability |
| G-08 | **All errors return HTTP 400** — no semantic status codes | **Medium** | Poor API consumer experience; impossible to programmatically distinguish error types | API Quality |
| G-09 | **No amount limits** — no min/max/daily limits | **High** | Enables money laundering, unlimited exposure per transaction | Compliance |
| G-10 | **No self-transfer prevention** | **Medium** | Accounting anomalies; potential exploit for transaction count inflation | Financial Integrity |
| G-11 | **Missing ISO identifiers** — no `MsgId`, `EndToEndId`, `InstrId`, `PmtInfId` | **High** | Cannot trace payments end-to-end; ISO 20022 migration impossible without them | ISO Compliance |
| G-12 | **No debtor/creditor party information** | **Medium** | Regulatory reporting (KYC, AML) cannot be attached to payment messages | ISO Compliance |
| G-13 | **No remittance information** — no memo/narration field | **Medium** | Customers cannot describe payment purpose; reconciliation difficulty | Usability |
| G-14 | **No payment method / purpose code** | **Low** | Cannot categorize payments for analytics or regulatory reporting | ISO Compliance |
| G-15 | **No requested execution date** — immediate only | **Medium** | No scheduled/future-dated payments capability | Feature Gap |
| G-16 | **No charge bearer indicator** | **Low** | Cannot model OUR/BEN/SHA fee structures | ISO Compliance |
| G-17 | **Status model too simple** — only 2-3 states vs. ISO's lifecycle | **Medium** | Cannot represent ACCP, ACSC, RJCT, CANC, etc. | ISO Compliance |
| G-18 | **No batch/bulk payment support** — single transaction per request | **Medium** | Enterprise clients cannot submit payroll/batch payments | Feature Gap |
| G-19 | **No concurrent access control** — no pessimistic locking on account balance | **High** | Race condition allows overdrafts under concurrent requests | Financial Integrity |
| G-20 | **Proprietary account numbers** — not IBAN format | **Low** | Cross-border interoperability limited; domestic-only acceptable | ISO Compliance |
| G-21 | **No Feign error decoder** — raw exceptions bubble up | **Medium** | Downstream errors crash callers with unintelligible stack traces | Reliability |
| G-22 | **No circuit breaker** — core banking failure cascades to all services | **High** | Full system outage when core banking is slow/down | Resilience |

### Critical Items Requiring Immediate Action

1. **G-02**: Fix double-deduction bug — direct financial loss on every transaction
2. **G-03**: Add idempotency keys — prevent duplicate charges
3. **G-04**: Add account ownership verification — prevent unauthorized transfers
4. **G-01**: Add currency to all payment DTOs — regulatory prerequisite
5. **G-06**: Add Bean Validation (`@Valid`, `@NotNull`, `@Positive`) — prevent crash-inducing input
