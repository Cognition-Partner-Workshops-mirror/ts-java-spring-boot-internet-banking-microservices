# Payment Payload Gap Analysis

## 1. Executive Summary

This document assesses the payment domain of the Internet Banking Microservices platform against ISO 20022 payment message standards. The analysis covers fund transfer and utility payment payloads, validation rules, and identifies critical gaps that expose the system to financial, regulatory, and operational risk.

**Overall Rating: HIGH RISK** — The current payment payloads carry only 3–4 fields each, whereas ISO 20022 standards require 20+ structured elements for interbank credit transfers. No currency handling, no idempotency, no duplicate detection, and no amount-limit enforcement exist in the codebase.

## 2. Current Payment Payload Structures

### 2.1 Fund Transfer — Request (internet-banking-fund-transfer-service)

| Field | Java Type | Description |
|-------|-----------|-------------|
| `fromAccount` | `String` | Source account number |
| `toAccount` | `String` | Destination account number |
| `amount` | `BigDecimal` | Transfer amount |
| `authID` | `String` | Authenticated user identifier (only in fund-transfer-service; stripped before forwarding to core-banking) |

**Source:** `FundTransferRequest.java` in `internet-banking-fund-transfer-service`

### 2.2 Fund Transfer — Request (core-banking-service)

| Field | Java Type | Description |
|-------|-----------|-------------|
| `fromAccount` | `String` | Source account number |
| `toAccount` | `String` | Destination account number |
| `amount` | `BigDecimal` | Transfer amount |

> **Note:** The `authID` field present in the fund-transfer-service DTO is absent from the core-banking-service DTO. This means the core-banking layer has no record of who authorized the transfer.

### 2.3 Fund Transfer — Response

| Field | Java Type | Description |
|-------|-----------|-------------|
| `message` | `String` | Human-readable status message |

## 3. ISO 20022 Comparison

### 3.1 Applicable ISO 20022 Message Types

| ISO 20022 Message | Purpose | Relevance |
|-------------------|---------|-----------|
| **pain.001** (CustomerCreditTransferInitiation) | Customer initiates a credit transfer | Maps to fund transfer request |
| **pain.002** (CustomerPaymentStatusReport) | Status report for a payment initiation | Maps to fund transfer / utility payment response |
| **pacs.008** (FIToFICustomerCreditTransfer) | Interbank credit transfer execution | Maps to core-banking internal fund transfer |

### 3.2 Fund Transfer vs. pain.001 (CustomerCreditTransferInitiation)

| ISO 20022 Field (pain.001) | Status | Current Field | Gap Detail |
|----------------------------|--------|---------------|------------|
| `MsgId` (Message Identification) | **MISSING** | — | No unique message identifier for the initiation request; prevents correlation and deduplication |
| `CreDtTm` (Creation Date Time) | **MISSING** | — | No timestamp on the request; only audit timestamps exist on the persisted entity |
| `NbOfTxs` (Number of Transactions) | **MISSING** | — | No batch support; each request is a single transaction with no explicit count |
| `CtrlSum` (Control Sum) | **MISSING** | — | No control sum for batch validation |
| `InitgPty` (Initiating Party) | **PARTIAL** | `authID` | The `authID` field captures the initiator but is not forwarded to core-banking; no structured party identification (name, address, org ID) |
| `PmtInfId` (Payment Information ID) | **MISSING** | — | No payment information block identifier |
| `PmtMtd` (Payment Method) | **MISSING** | — | Always assumed to be credit transfer; no explicit method field |
| `ReqdExctnDt` (Requested Execution Date) | **MISSING** | — | No scheduled/future-dated payment support |
| `Dbtr` (Debtor) | **PARTIAL** | `fromAccount` | Only the account number is sent; no debtor name, address, or identification |
| `DbtrAcct` (Debtor Account) | **PARTIAL** | `fromAccount` | Account number only; no IBAN, account type, or currency fields |
| `DbtrAgt` (Debtor Agent / Bank BIC) | **MISSING** | — | No bank identification (BIC/SWIFT); assumes single institution |
| `CdtrAgt` (Creditor Agent / Bank BIC) | **MISSING** | — | No creditor bank identification |
| `Cdtr` (Creditor) | **PARTIAL** | `toAccount` | Only the account number; no creditor name, address, or identification |
| `CdtrAcct` (Creditor Account) | **PARTIAL** | `toAccount` | Account number only; no IBAN or currency |
| `Amt/InstdAmt` (Instructed Amount) | **PARTIAL** | `amount` | Amount is present but **no currency code** (ISO 4217). System implicitly assumes a single currency |
| `RmtInf` (Remittance Information) | **MISSING** | — | No payment reference, invoice number, or unstructured/structured remittance data |
| `Purp` (Purpose) | **MISSING** | — | No transaction purpose code |
| `ChrgBr` (Charge Bearer) | **MISSING** | — | No indication of who bears the charges (SHA/BEN/OUR) |
| `InstrId` (Instruction Identification) | **MISSING** | — | No unique instruction ID for end-to-end tracking |
| `EndToEndId` (End-to-End Identification) | **MISSING** | — | No end-to-end identifier that travels through the entire payment chain |

| `CdtTrfTxInf/ChrgBr` | **MISSING** | — | No charge bearer |
| `CdtTrfTxInf/Dbtr` | **MISSING** | — | Only account entity reference; no structured debtor info |
| `CdtTrfTxInf/Cdtr` | **MISSING** | — | Only account entity reference; no structured creditor info |

## 4. Payment Validation Rules Assessment

### 4.1 Amount Limits

| Validation | Implemented? | Detail |
|------------|-------------|--------|
| Minimum transfer amount | **NO** | Zero or negative amounts are accepted without error |
| Maximum transfer amount | **NO** | No per-transaction limit; no daily/weekly/monthly cumulative limits |
| Zero-amount check | **NO** | `BigDecimal` allows `0.00` and negative values with no guard |
| Decimal precision enforcement | **NO** | No rounding rules; `BigDecimal` scale is not constrained |

### 4.2 Currency Handling

| Validation | Implemented? | Detail |
|------------|-------------|--------|
| Currency code field | **NO** | No currency field on any request or entity |
| Multi-currency support | **NO** | Entire system implicitly operates in a single unnamed currency |
| FX rate handling | **NO** | No foreign exchange rate or conversion logic |
| Currency mismatch check | **NO** | Cannot occur since currency is absent |

### 4.3 Duplicate Detection

| Validation | Implemented? | Detail |
|------------|-------------|--------|
| Request-level duplicate check | **NO** | Identical requests submitted in rapid succession will each create a new transaction |
| Idempotency key | **NO** | No `Idempotency-Key` header or field on any POST endpoint |
| Transaction reference uniqueness | **NO** | `transactionId` is a server-generated UUID, not client-supplied; no deduplication window |

### 4.4 Idempotency

| Validation | Implemented? | Detail |
|------------|-------------|--------|
| Idempotent POST endpoints | **NO** | Fund transfer and utility payment POSTs are not idempotent |
| Retry safety | **NO** | Network timeouts or client retries will create duplicate transactions |
| At-most-once delivery | **NO** | No mechanism to guarantee at-most-once semantics |

### 4.5 Account Validation

| Validation | Implemented? | Detail |
|------------|-------------|--------|
| Account existence check | **YES** | `AccountService.readBankAccount()` throws `EntityNotFoundException` if account is missing |
| Account status check | **NO** | DORMANT or BLOCKED accounts are not rejected; any existing account can transact |
| Self-transfer check | **NO** | Transferring from and to the same account is allowed |
| Account ownership validation | **NO** | Any authenticated user can transfer from any account; no ownership verification against `authID` |

### 4.6 Balance Validation

| Validation | Implemented? | Detail |
|------------|-------------|--------|
| Sufficient balance check | **YES** | `validateBalance()` compares `actualBalance` against the requested amount |
| Double-deduction bug | **BUG** | `internalFundTransfer()` and `utilPayment()` in `TransactionService` set `availableBalance = actualBalance - amount` after already subtracting amount from `actualBalance`, causing a double subtraction |
| Concurrent balance check (optimistic locking) | **NO** | No `@Version` on `BankAccountEntity`; race conditions can lead to overdrafts |
| Available vs. actual balance distinction | **BROKEN** | Due to the double-deduction bug, `availableBalance` diverges from its intended value |

## 5. Gap Severity and Business Risk Rating

| # | Gap | Severity | Business Risk | ISO 20022 Ref |
|---|-----|----------|---------------|---------------|
| G-01 | **Double-deduction bug** — `availableBalance` computed from already-debited `actualBalance` | **CRITICAL** | Direct financial loss; incorrect account balances | pacs.008 settlement |
| G-02 | **No idempotency / duplicate detection** — retries create duplicate transactions | **CRITICAL** | Financial loss from double-charging customers | pain.001 `MsgId`, `InstrId` |
| G-03 | **No amount validation** — zero, negative, or extreme amounts accepted | **CRITICAL** | Fraudulent or erroneous transactions; regulatory non-compliance | pain.001 `InstdAmt` rules |
| G-04 | **No currency code** — entire system is currency-blind | **HIGH** | Cannot support multi-currency; violates ISO 4217 requirements; regulatory gap | pain.001 `InstdAmt@Ccy` |
| G-05 | **No account status validation** — DORMANT/BLOCKED accounts can transact | **HIGH** | Transactions on frozen accounts; compliance violation | N/A (operational) |
| G-06 | **No account ownership validation** — any user can debit any account | **CRITICAL** | Unauthorized fund transfers; major security vulnerability | pain.001 `Dbtr` / `InitgPty` |
| G-07 | **No concurrent balance protection** — no optimistic locking on account entity | **HIGH** | Race condition overdrafts under concurrent requests | pacs.008 settlement |
| G-08 | **No end-to-end identifier** — cannot trace a payment through the chain | **HIGH** | Operational blind spot; no audit trail across services | pain.001 `EndToEndId` |
| G-09 | **No structured error responses** — all errors return HTTP 400 with free text | **HIGH** | Client cannot programmatically handle different failure types | pain.002 `StsRsnInf` |
| G-10 | **No remittance information** — no payment reference or invoice data | **MEDIUM** | Cannot support reconciliation or regulatory reporting requirements | pain.001 `RmtInf` |
| G-11 | **No debtor/creditor party information** — only account numbers, no names/addresses | **MEDIUM** | Cannot comply with name-screening, sanctions, or AML requirements | pain.001 `Dbtr`, `Cdtr` |
| G-12 | **No requested execution date** — all transfers are immediate | **MEDIUM** | No future-dated payment capability; limits product offering | pain.001 `ReqdExctnDt` |
| G-13 | **No payment method field** — always assumed credit transfer | **LOW** | Cannot distinguish between payment types (DD, CT, cheque) | pain.001 `PmtMtd` |
| G-14 | **No charge bearer** — no indication of who pays fees | **LOW** | Cannot support OUR/BEN/SHA fee models | pain.001 `ChrgBr` |
| G-15 | **No batch payment support** — single transaction per request only | **LOW** | Cannot process payroll or bulk payments efficiently | pain.001 `NbOfTxs` |
| G-16 | **No settlement information** — no clearing system or settlement account | **LOW** | Limits to internal book transfers only | pacs.008 `SttlmInf` |
| G-17 | **No transaction purpose code** | **LOW** | Cannot categorize transactions for regulatory reporting | pain.001 `Purp` |
| G-18 | **authID not forwarded to core-banking** — audit trail broken | **HIGH** | Core ledger has no record of who authorized each transaction | pain.001 `InitgPty` |
| G-19 | **No compensation/rollback on Feign failure** — transactions stuck in PENDING/PROCESSING | **CRITICAL** | Funds debited but status never updated; manual intervention required | pain.002 status lifecycle |
| G-20 | **Self-transfer allowed** — fromAccount == toAccount not checked | **MEDIUM** | Potential for confusion or exploitation of edge cases | N/A (operational) |

## 7. Recommendations Priority

1. **Immediate (Sprint 1):** Fix the double-deduction bug (G-01), add amount validation (G-03), add account ownership validation (G-06), add idempotency keys (G-02)
2. **Short-term (Sprint 2–3):** Add currency support (G-04), account status checks (G-05), optimistic locking (G-07), end-to-end IDs (G-08), compensation/rollback logic (G-19), forward authID to core-banking (G-18)
3. **Medium-term (Sprint 4–6):** Structured error responses (G-09), remittance information (G-10), debtor/creditor party data (G-11), execution date support (G-12), self-transfer check (G-20)
4. **Long-term (Sprint 7+):** Batch payment support (G-15), settlement information (G-16), purpose codes (G-17), payment method (G-13), charge bearer (G-14)
