## 1. Architecture Overview

### 1.1 Services

| # | Service | Port | Role |
|---|---------|------|------|
| 1 | **internet-banking-service-registry** | 8081 | Netflix Eureka server — central service registry for discovery |
| 2 | **internet-banking-config-server** | 8090 | Spring Cloud Config server — externalised configuration from a [Git repository](https://github.com/JavatoDev-com/internet-banking-microservices-configurations.git) |
| 3 | **internet-banking-api-gateway** | 8082 | Spring Cloud Gateway — single entry-point; routes requests, enforces OAuth 2.0 JWT security |
| 4 | **internet-banking-user-service** | 8083 | User registration, approval/update, Keycloak identity management |
| 5 | **internet-banking-fund-transfer-service** | 8084 | Orchestrates fund transfers between bank accounts via core-banking-service |
| 6 | **internet-banking-utility-payment-service** | 8085 | Orchestrates utility bill payments via core-banking-service |
| 7 | **core-banking-service** | 8092 | Banking core — accounts, users, transactions, balance management |

> **Note:** A *Notification Service* (RabbitMQ consumer) is referenced in the README but not yet implemented.

### 1.2 Communication Patterns

| Pattern | Technology | Usage |
|---------|-----------|-------|
| Synchronous REST | **OpenFeign** (via Eureka service discovery) | `user-service → core-banking-service`, `fund-transfer-service → core-banking-service`, `utility-payment-service → core-banking-service` |
| API Gateway routing | **Spring Cloud Gateway** | External clients → gateway → downstream services (path-based routing) |
| Service discovery | **Netflix Eureka** | All business services register with Eureka; Feign clients resolve service names |
| Centralised config | **Spring Cloud Config** (Git-backed) | All services fetch configuration at boot via `bootstrap.yml` / `bootstrap-docker.yml` |
| Authentication header propagation | Custom `GlobalFilter` in API Gateway | Extracts principal name and injects `X-Auth-Id` header to downstream services |
| Auth user context | `AppAuthUserFilter` (Servlet Filter) | Downstream services read `X-Auth-Id` and store it in a `ThreadLocal`-based `ApiRequestContextHolder` for JPA auditing |
| Distributed tracing | **Micrometer Tracing + Zipkin** (Brave bridge) | Trace/span IDs propagated across services; spans exported to Zipkin |

### 1.3 Infrastructure Components

| Component | Image / Tech | Purpose |
|-----------|-------------|---------|
| MySQL 8 | Custom Dockerfile (see `docker-compose/mysql/`) | Persistent storage for core-banking, fund-transfer, user, and utility-payment services (4 databases) |
| Keycloak 23.0.7 | `quay.io/keycloak/keycloak:23.0.7` | OAuth 2.0 / OpenID Connect identity provider; realm pre-imported |
| PostgreSQL 15 | `postgres:15` | Keycloak's backing store |
| Zipkin 3 | `openzipkin/zipkin:3` | Distributed trace collection and UI |

## 3. API Surface Map

### 3.1 API Gateway Routes (Port 8082)

All external traffic enters through the gateway. The gateway prefixes downstream service paths:

| Gateway Path Prefix | Downstream Service |
|---------------------|-------------------|
| `/user/**` | internet-banking-user-service |
| `/fund-transfer/**` | internet-banking-fund-transfer-service |
| `/utility-payment/**` | internet-banking-utility-payment-service |
| `/banking-core/**` | core-banking-service |

**Security:** All endpoints require a valid JWT except:
- `POST /user/api/v1/bank-users/register` — open for user registration
- `/actuator/**` and `/{service}/actuator/**` — open for health / info checks

## 4. Key Business Logic Inventory

### 4.1 User Registration Flow

1. Client sends `POST /user/api/v1/bank-users/register` with email, identification (NIC), and password.
2. **User Service** checks Keycloak for existing email → rejects if found (`UserAlreadyRegisteredException`).
3. Calls **Core Banking Service** (`GET /api/v1/user/{identification}`) to validate the user exists in the banking core.
4. Validates email matches the core record → rejects on mismatch (`InvalidEmailException`).
5. Creates a Keycloak user (disabled, unverified) with provided credentials.
6. Persists a local `UserEntity` with status `PENDING` and Keycloak `authId`.

### 4.2 User Approval Flow

1. Admin sends `PATCH /user/api/v1/bank-users/update/{id}` with status `APPROVED`.
2. **User Service** reads the Keycloak user via `authId`.
3. Enables the Keycloak user and marks email as verified.
4. Updates local status to `APPROVED`.

### 4.3 Fund Transfer Flow

1. Client sends `POST /fund-transfer/api/v1/transfer` with fromAccount, toAccount, amount.
2. **Fund Transfer Service** persists a local `FundTransferEntity` with status `PENDING`.
3. Calls **Core Banking Service** (`POST /api/v1/transaction/fund-transfer`) via Feign.
4. Core Banking validates both accounts exist and verifies sufficient funds in the source account.
5. Deducts amount from source account (`actualBalance` and `availableBalance`).
6. Credits amount to destination account.
7. Records two `TransactionEntity` records (debit + credit) with the same `transactionId`.
8. Returns `transactionId` → Fund Transfer Service updates local record to `SUCCESS`.

### 4.4 Utility Payment Flow

1. Client sends `POST /utility-payment/api/v1/utility-payment` with providerId, amount, referenceNumber, account.
2. **Utility Payment Service** persists a local `UtilityPaymentEntity` with status `PROCESSING`.
3. Calls **Core Banking Service** (`POST /api/v1/transaction/util-payment`) via Feign.
4. Core Banking validates the source account and verifies sufficient funds.
5. Looks up the utility provider account by `providerId`.
6. Deducts amount from the source bank account.
7. Records a `TransactionEntity` of type `UTILITY_PAYMENT`.
8. Returns `transactionId` → Utility Payment Service updates local record to `SUCCESS`.

### 4.5 Balance Validation Rules

- The `validateBalance` method in `TransactionService` checks:
  - `actualBalance >= 0`
  - `actualBalance >= requestedAmount`
- Throws `InsufficientFundsException` with error code `BANKING-CORE-SERVICE-1001` on failure.

### 4.6 Audit Trail

- Fund Transfer, Utility Payment, and User services use JPA Auditing (`@EntityListeners(AuditingEntityListener.class)`).
- `createdBy` / `modifiedBy` populated from `ApiRequestContextHolder` (fed by `X-Auth-Id` header from gateway).
- Optimistic locking via `@Version` field on all audited entities.

## 6. Build and Deployment Pipeline Summary

### 6.1 Build System

- **Gradle 8.6** — each service has its own `gradlew` wrapper (no root multi-project build).
- **Java 21** — `sourceCompatibility = '21'` in all `build.gradle` files.
- **Spring Boot 3.2.4** — applied via `org.springframework.boot` plugin.
- **Spring Cloud 2023.0.0** — managed via `spring-cloud-dependencies` BOM.
- **Git Properties Plugin** — `com.gorylenko.gradle-git-properties:2.4.2` generates `git.properties` for `/actuator/info`.

### 6.2 Build Commands

```bash
# Build all services (skip tests for speed)
for svc in internet-banking-service-registry internet-banking-config-server \
           internet-banking-api-gateway internet-banking-user-service \
           internet-banking-fund-transfer-service internet-banking-utility-payment-service \
           core-banking-service; do
  (cd "$svc" && ./gradlew build -x test)
done

# Run tests
for svc in core-banking-service internet-banking-user-service \
           internet-banking-fund-transfer-service internet-banking-utility-payment-service; do
  (cd "$svc" && ./gradlew test)
done
```

### 6.3 Docker

- Each service has a `Dockerfile` based on `eclipse-temurin:21.0.2_13-jre-alpine`.
- Uses `wait-for-it.sh` to ensure dependency ordering (config-server, service-registry, MySQL).
- Docker profile activated via `-Dspring.profiles.active=docker`.

### 6.4 Docker Compose

- **`docker-compose.yml`** — full stack: Zipkin, Keycloak + PostgreSQL, MySQL, all 7 services.
- **`docker-compose-support-apps.yml`** — infrastructure only: Zipkin, Keycloak + PostgreSQL, MySQL, config-server, service-registry.
- Static IP addressing on a custom bridge network (`172.25.0.0/16`).
- Named volumes for MySQL and PostgreSQL data persistence.

### 6.5 Database Initialisation

- **Core Banking:** Flyway migrations under `src/main/resources/db/migration/` create base tables and seed test data.
- **Other services:** Schema auto-generated by Hibernate (via config-server settings, likely `ddl-auto: update`).
- **MySQL init:** `docker-compose/mysql/privileges.sql` creates the DB user and 4 databases.
